# ТЗ на исправление компонента оформления заказа `/oformlenie-zakaza/`

Основание: аудит, выполненный в [`docs/oformlenie-zakaza.md`](oformlenie-zakaza.md).
Область: компонент `opensource:order` + шаблон `order-page` (десктоп `fisheat`, приложение `fisheat_app`, `mobile_app`), модули `ldo.marketing`, `ldo.develop`.

---

## 0. Соглашения и ограничения

- **Три копии шаблона.** Все правки шаблона выполняются в `fisheat`, затем переносятся в `fisheat_app` и `mobile_app` (или переводится на единый шаблон — задача TZ-18).
- **Композит.** Страница зависит от `$_SESSION` (купоны, подарок, бонусы) — итоговое состояние разметки не должно кешироваться композитом (TZ-14).
- **PHP CLI.** Bitrix в этой сборке запускается только на PHP 8.1 (`modules/php/PHP_8.1/php.exe`); отладка через CLI — на 8.1.
- **Совместимость.** Не ломать существующие AJAX-контракты: `addQuantity`, `deleteProduct`, `removeCart`, `changePromo`, `clearPromo`, `addAddress`, `editAddress`, `deleteAddress`, `getBasketItemData`, `updateDeliveryPrice`, `updateAddressPrice`, `updateRestaurantPrice`.
- **Терминология.**
  - *Зачётные товары* — позиции корзины, которые участвуют в расчёте порогов и минимальной суммы: обычные товары пользователя (без подарочных и бесплатных позиций).
  - *Подарок* — товар из уровня `ldo_marketing_gift_levels`, который пользователь выбирает на странице (1 подарок на заказ).
  - *Уровень подарка* — строка `GiftsTable`: `NAME` (название), `SUM` (порог), `PRODUCT_IDS` (JSON ID подарков).

## 2. TZ-01. Добавление подарка в корзину и заказ

### 2.1 Проблема
Свойство заказа `GIFT` (`ID=24`, `UTIL=Y`, `TYPE=NUMBER`) заполняется ID товара, но **никем не читается**: в `b_sale_discount` нет правил с `GIFT` (проверено запросом — 0 совпадений), в коде обработчиков нет. Фактически подарок пользователю не выдаётся.

### 2.2 Требуемое поведение
1. Пользователь выбирает подарок → в корзине появляется позиция этого товара с ценой 0 ₽.
2. Позиция-подарок помечена как подарочная и **не участвует** в расчёте: порогов подарков, минимальной суммы заказа, количества бесплатных позиций.
3. Подарок всегда один: выбор нового удаляет предыдущую подарочную позицию.
4. При отмене подарка позиция удаляется из корзины.
5. При недоступности (сумма ниже порога) — позиция и сессия сбрасываются.
6. Оформить заказ нельзя, если подарок выбран, но стал недоступен (проверка в `validateOrder`).

### 2.3 Реализация

Создать сервис `local/modules/ldo.marketing/lib/GiftService.php`:

```php
namespace Ldo\Marketing;

class GiftService
{
    /** Признак подарочной позиции в свойствах позиции корзины */
    public const BASKET_PROP_CODE = 'GIFT_AUTO';

    /** Карта: productId => ['LEVEL' => string, 'SUM' => int] по активным уровням сайта */
    public static function getProductsMap(string $siteId): array;

    /** Проверка: является ли товар подарком какого-либо активного уровня */
    public static function isGiftProduct(int $productId, string $siteId): bool;

    /** Порог уровня для товара-подарка (0, если товар не подарок) */
    public static function getGiftThreshold(int $productId, string $siteId): int;

    /** Максимальный порог среди доступных уровней (для проверки суммы) */
    public static function getMaxAvailableThreshold(float $chargeableSum, string $siteId): int;

    /**
     * Синхронизация корзины с выбранным подарком.
     * @param \Bitrix\Sale\Basket $basket
     * @param int $giftProductId 0 — удалить подарок
     */
    public static function syncGift(\Bitrix\Sale\Basket $basket, int $giftProductId): void;

    /** Удалить все подарочные позиции */
    public static function removeGift(\Bitrix\Sale\Basket $basket): void;

    /** Является ли позиция подарочной */
    public static function isGiftItem(\Bitrix\Sale\BasketItem $item): bool;

    /** Зачётная сумма корзины (без подарочных и бесплатных позиций) */
    public static function getChargeableSum(\Bitrix\Sale\Basket $basket): float;
}
```

`syncGift()`:
1. Пройти корзину, удалить все позиции с `BasketPropertyItem['GIFT_AUTO'] = 'Y'`.
2. Если `$giftProductId <= 0` — выйти (результат: подарка нет).
3. Проверить `isGiftProduct($giftProductId, $siteId)`; если нет — выйти.
4. Создать позицию: `$basket->createItem('catalog', $giftProductId)`, `QUANTITY = 1`, `CURRENCY`, `LID`;
   установить `CUSTOM_PRICE = 'Y'`, `BASE_PRICE = 0`, `DISCOUNT_PRICE = 0`, `PRICE = 0`.
5. Добавить свойство позиции `GIFT_AUTO = 'Y'` (и `GIFT_LEVEL = <NAME>` для аналитики) через `$item->getPropertyCollection()->createItem([...])` (по аналогии с `BasketPropertyItem`).
6. Вернуть флаг `basketChanged` для вызова `save()`.

Вызовы `syncGift()`:
| Точка | Что делать |
|---|---|
| `setGiftAction()` (после записи сессии) | `syncGift($basket, $giftId)` + `$basket->save()` + вернуть `prepareBasketResponse()` |
| `createVirtualOrder()` (страница оформления) | `syncGift($basket, (int)$_SESSION['LDO_GIFT_ID'])` — как сейчас вызывается `applyFreePositionsToCurrentBasket()` |
| `addQuantityAction()`, `deleteProductAction()`, `removeCartAction()` | `syncGift()` после изменения количества/удаления |
| `executeComponent()` при `SAVE` | ничего дополнительно (позиция уже в корзине), но при `giftId = 0` — удалить подарок |

Дополнительно зарегистрировать в `local/php_interface/init.php` обработчик `OnSaleBasketBeforeSaved` (или `OnSaleBasketItemSaved`), который вызывает `GiftService::syncGift()` с защитой от рекурсии (флаг по аналогии с `Basket::$freePositionsSyncing`), чтобы подарок восстанавливался после любого пересчёта корзины (в т.ч. синхронизации бесплатных позиций).

### 2.4 Исключение подарка из расчётов
Во всех местах, где считается сумма, добавить фильтр `GiftService::isGiftItem($item)`:
- `OpenSourceOrderComponent::validateMinOrderSum()` — считать только зачётные товары;
- `OpenSourceOrderComponent::calculateTotalsInOrderContext()` — подарочные позиции не должны добавляться в `baseSum/totalPrice` (их цена 0, но они влияют на количество и правила);
- `prepareBasketResponse()` — подарочные позиции выводить в `items`, но помечать `isGift: true`, чтобы JS не показывал для них «±», цену и вес;
- `result_modifier.php` — базой для порогов подарков должна быть **зачётная сумма** (см. TZ-06);
- `Basket::syncFreePositions()` — подарочные товары не должны учитываться при подсчёте «штук» по разделам (исключать по `isGiftItem`), иначе подарок даст лишние бесплатные позиции.

### 2.5 Критерии приёмки
- **Given** сумма корзины ≥ 500 ₽, **When** пользователь нажимает «Выбрать» у подарка, **Then** подарок появляется в списке товаров с ценой `0 ₽` и плашкой «Подарок», в свойстве заказа `GIFT` записан ID, в админке заказ содержит позицию-подарок.
- **Given** выбран подарок, **When** пользователь выбирает другой подарок, **Then** в корзине ровно одна подарочная позиция — новая.
- **Given** выбран подарок, **When** пользователь нажимает «Отменить», **Then** позиция удалена из корзины, свойство `GIFT` пусто, сессия очищена.
- **Given** сумма корзины уменьшена ниже порога, **When** выполняется пересчёт, **Then** подарок снят в UI, удалён из корзины, свойство `GIFT` пусто.
- Подарочная позиция не увеличивает «Сумму заказа» и не помогает достичь минимальной суммы.

### 2.6 Риски
- Цена подарка может «перезаписываться» провайдером каталога → обязательно `CUSTOM_PRICE = 'Y'` до установки `PRICE`.
- Правила корзины могут давать скидку на подарочную позицию (не повлияет, цена 0) или считать её в условиях («сумма корзины») — проверить правила ID=3/4/5 и при необходимости использовать `DISCOUNT_EXCLUDE`/условие по свойству позиции.
- Двойной пересчёт корзины (подарок + бесплатные позиции) → защита от рекурсии обязательна.

## 3. TZ-02. Серверная валидация выбора подарка

### 3.1 Проблема
`setGiftAction()` принимает любой `giftId` без проверок: можно записать чужой/несуществующий товар, подарок из другого сайта или недоступного уровня.

### 3.2 Требования и реализация
В `setGiftAction()` при `giftId > 0`:

```php
$siteId = Context::getCurrent()->getSite();
Loader::includeModule('ldo.marketing');

if (!\Ldo\Marketing\GiftService::isGiftProduct($giftId, $siteId)) {
    return ['success' => false, 'error' => 'Этот подарок недоступен'];
}

$threshold = \Ldo\Marketing\GiftService::getGiftThreshold($giftId, $siteId);
$chargeableSum = \Ldo\Marketing\GiftService::getChargeableSum($this->getBasket());

if ($chargeableSum < $threshold) {
    return [
        'success' => false,
        'error' => 'Подарок доступен при заказе от ' . $threshold . ' ₽',
        'available' => false,
    ];
}
```

Дополнительно:
- проверять, что уровень активен и `SITE_ID` совпадает с текущим сайтом;
- при `giftId = 0` — только `unset($_SESSION['LDO_GIFT_ID'])` + удаление подарочной позиции.

### 3.3 Критерии приёмки
- Запрос `setGift` с ID обычного (не подарочного) товара → `success: false`, свойство не меняется.
- Запрос с валидным подарком при сумме ниже порога → `success: false`, сообщение с порогом.
- Прямой AJAX-запрос в обход UI не позволяет получить подарок бесплатно.

## 4. TZ-03. Взаимоисключение «подарок ↔ промокод ↔ бонусы»

### 4.1 Проблема
Предупреждение «использование промокода и списание бонусов будет невозможно» реализовано **только** визуальным оверлеем `.block`. Применённый купон остаётся, скидка продолжает работать вместе с подарком; бонусы не сбрасываются.

### 4.2 Требуемое поведение (сервер — источник истины)
| Действие | Серверная реакция |
|---|---|
| Выбор подарка (`setGift`, `giftId > 0`) | Снять купоны и обнулить бонусы; вернуть флаг `promoCleared: true` |
| Применение промокода (`changePromo`) | Если выбран подарок — снять подарок; вернуть флаг `giftCleared: true` |
| Отмена подарка (`setGift`, `giftId = 0`) | Промокод не восстанавливаем (пользователь вводит заново); вернуть `promoAvailable: true` |

### 4.3 Реализация

**`setGiftAction()`** при успешном выборе подарка:
```php
// 1. Снять купоны
if (Sale\DiscountCouponsManager::getCountApplied() > 0) {
    Sale\DiscountCouponsManager::clear(true);
    $promoCleared = true;
}
// 2. Обнулить бонусы
if (!empty($_SESSION['BONUS_PAY_USER_VALUE'])) {
    unset($_SESSION['BONUS_PAY_USER_VALUE']);
    $promoCleared = true;
}
// 3. Пересчитать корзину
$basket->refreshData(['PRICE', 'COUPONS']);
$basket->save();
// 4. Вернуть как prepareBasketResponse + флаги
```

**`changePromoAction()`** при успешном применении купона:
```php
if (!empty($_SESSION['LDO_GIFT_ID'])) {
    unset($_SESSION['LDO_GIFT_ID']);
    GiftService::removeGift($this->getBasket());
    $this->applyGiftPropertyFromSession(); // в новом виртуальном заказе свойство = ''
    $giftCleared = true;
}
```

**UI (`script.js`)**:
- `applyGiftSelection()`: после ответа `setGift` с `promoCleared` — очистить `#promocode`, снять `checked` с `radio[name=promo_id]`, вернуть кнопку промокода в состояние «Применить», показать уведомление «Промокод и бонусы сброшены»; обновить список товаров (подарок появился).
- `applyPromoCode()`: при `giftCleared` — снять `selected` с подарка, вернуть «Выбрать», `BX.removeClass('.promo-block','block')`, снять `block` с `.gifts-block`, показать уведомление.
- Блокировку промокода классом `block` оставить как визуальное усиление (не как единственную защиту).

### 4.4 Критерии приёмки
- Купон применён → выбор подарка → купон снят, сумма пересчитана без скидки, UI показывает пустое поле промокода.
- Подарок выбран → ввод промокода → подарок снят с корзины и UI, свойство `GIFT` пусто.
- Обход через прямой AJAX даёт тот же результат.

## 5. TZ-04. Рабочая отмена промокода

### 5.1 Проблема
`bindPromoEvents()` навешивает один обработчик на `.promoChange button`, который всегда вызывает `applyPromoCode()`. При применённом купоне кнопка подписана «Отменить», но выполняется повторное применение; `clearPromoAction` из JS не вызывается.

### 5.2 Реализация
1. В `form.php` кнопке добавить атрибут действия, зависящий от состояния купона:
```php
<button type="button" data-promo-action="<?= $_SESSION['CATALOG_USER_COUPONS'] ? 'clear' : 'apply' ?>">
    <?= $_SESSION['CATALOG_USER_COUPONS'] ? 'Отменить' : 'Применить' ?>
</button>
```
2. В `bindPromoEvents()`:
```js
BX.bind(promoButton, 'click', BX.proxy(function (e) {
    e.preventDefault(); e.stopPropagation();
    if (promoButton.getAttribute('data-promo-action') === 'clear') {
        this.clearPromoCode();
    } else {
        this.applyPromoCode();
    }
}, this));
```
3. Новый метод `clearPromoCode()`:
```js
clearPromoCode: function () {
    BX.ajax.runComponentAction('opensource:order', 'clearPromo', {
        mode: 'class', dataType: 'json',
        data: { dataPromo: { sessid: BX.bitrix_sessid() } }
    }).then(function (response) {
        if (!response.data || !response.data.success) { this.showNotice(response.data.error); return; }
        var input = document.getElementById('promocode');
        if (input) { input.value = ''; input.readOnly = false; }
        var btn = document.querySelector('.promoChange button');
        if (btn) { btn.textContent = 'Применить'; btn.setAttribute('data-promo-action', 'apply'); }
        document.querySelectorAll('input[name="promo_id"]').forEach(function (r) { r.checked = false; });
        BX.removeClass(document.querySelector('.gifts-block'), 'block');
        this.updateAllItemsPrices(response.data.items);
        this.updateAllTotals({ deliveryPrice: response.data.deliveryPrice, baseSum: response.data.baseSum,
                               discount: response.data.discount, total: response.data.totalPrice });
        this.showNotice('Промокод отменён');
    }.bind(this)).catch(function (e) { this.showNotice('Ошибка соединения'); }.bind(this));
}
```
4. `applyPromoCode()`: после успеха обновлять `data-promo-action="clear"`, `readOnly = true`, `checked` radio «Промокод».

### 5.3 Критерии приёмки
- Купон применён → кнопка «Отменить» → купон снят, цены и итоги пересчитаны, поле промокода пустое и доступно для ввода, блок подарков разблокирован.
- Повторное применение того же промокода работает.

## 6. TZ-05. Бонусы: устранение неопределённой переменной и незавершённой интеграции

### 6.1 Проблема
В [`form.php:513`](../local/templates/fisheat/components/opensource/order/order-page/form.php:513) выводится `$arResultEx['BONUS']['ORDER']['VALUE_FORMAT']`, хотя `$arResultEx` определяется только внутри закомментированного блока выше → пусто и PHP-notice. Блок оплаты бонусами закомментирован, но radio «Оплата бонусами» и JS-заглушки остались; обработчик `OnSaleOrderSaved` для `acrit.bonus` в `oformlenie-zakaza/index.php` активен.

### 6.2 Решение — выбрать один вариант
**Вариант A (рекомендуемый, если бонусы не внедряются):**
- удалить строку «Начислено бонусов» из `form.php` (правый блок итогов) и весь закомментированный блок acrit (строки ~366–401, ~540–574);
- убрать radio «Оплата бонусами» из `.promo-block`;
- удалить из `script.js` методы `showBonusBlock`, `hideBonusBlock`, `handlePromoTypeChange`-ветку `bonus`;
- удалить `AcritBonusInOrderOpensourceIntegration::init()` из `oformlenie-zakaza/index.php`.

**Вариант B (если бонусы внедряются):**
- в `result_modifier.php` корректно инициализировать `$arResultEx` (или `$arResult['BONUS']`) при `Loader::includeModule('acrit.bonus')`, передавать в шаблон `BONUS_ORDER_VALUE`;
- раскомментировать и доработать блок оплаты бонусами (ввод суммы, применение, отображение в итогах);

## 7. TZ-06. Единая база расчёта порогов и минимальной суммы

### 7.1 Проблема
Пороги подарков считаются от разных величин:
- сервер (`result_modifier.php`): `PRODUCTS_PRICE` — товары **со скидками**;
- сервер (`validateMinOrderSum`): сумма **базовых** цен;
- JS (`recalcGiftsAvailability`): `totalPrice` из `prepareBasketResponse` (скидки без контекста заказа).
Из-за этого состояние кнопок подарков и блокировки оформления может «прыгать» и не совпадать с финальным расчётом.

### 7.2 Решение
Ввести один серверный метод и передавать его результат в шаблон и AJAX:

```php
/**
 * Сумма зачётных товаров для порогов (без подарочных и бесплатных позиций).
 * Считается по базовым ценам, без скидок и без доставки.
 */
public function getChargeableBaseSum(): float;
```

Правила:
- Порог подарка сравнивается с `getChargeableBaseSum()` — одинаково в `result_modifier.php`, `setGiftAction()` и `validateMinOrderSum()`.
- В шаблон передаётся `$arResult['CHARGEABLE_SUM']`; в `.gifts-list` выводится `data-chargeable-sum="..."`.
- `recalcGiftsAvailability()` использует `data-chargeable-sum` (обновляется при каждом AJAX-ответе — добавить поле `chargeableSum` в `prepareBasketResponse`), а не `totalPrice`.
- Минимальная сумма заказа сравнивается с этой же величиной (сейчас — с базовыми ценами; привести к единому виду).

### 7.3 Критерии приёмки
- Значение порога в UI совпадает с серверным при любых операциях с корзиной/скидками.
- После применения промокода порог подарка не «проседает» за счёт скидки (порог считается без скидок), а текст «До подарка осталось …» совпадает с расчётом на сервере при перезагрузке страницы.

## 8. TZ-07. Скидки в контексте заказа в ответах корзины

### 8.1 Проблема
`prepareBasketResponse()` применяет скидки через `Discount::buildFromBasket()` — без учёта выбранной службы доставки, поэтому в AJAX-ответе не срабатывают правила с условием «Способ доставки» (например `ID=6` «Скидка самовывоза»). Финальный расчёт (`calculateTotalsInOrderContext`) даёт другой результат → расхождение сумм.

### 8.2 Решение
1. Ввести в компоненте поля состояния текущего выбора: `$this->currentDeliveryId`, `$this->currentAddressId`, сохраняемые в сессию в `updateDeliveryPriceAction` / `updateAddressPriceAction` / `updateRestaurantPriceAction` (`LDO_DELIVERY_ID`, `LDO_ADDRESS_ID`).

3. Оптимизация (TZ-13): расчёт выполнять один раз на запрос и кэшировать в свойстве компонента.

### 8.3 Критерии приёмки
- При самовывозе и включённом правиле «Скидка самовывоза» сумма в AJAX-ответе (после «+/−») равна сумме при перезагрузке страницы.

## 12. TZ-11. Проверка прав на адреса (безопасность)

### 12.1 Проблема
`deleteAddressAction($dataAddress)` и `editAddressAction($dataAddress)` принимают произвольный `addressId` и выполняют действие без проверки, что адрес принадлежит текущему пользователю → любой авторизованный пользователь может удалить/изменить чужой адрес (`addressId` перебирается).

### 12.2 Реализация
Во всех экшенах, работающих с адресом, добавить проверку владельца:

```php
global $USER;
$address = \Ldo\Iiko\UserAddress::getById($addressId);
if (!$address || (int)$address['USER_ID'] !== (int)$USER->GetID()) {
    return ['success' => false, 'error' => 'Адрес не найден'];
}
```

Применить в: `deleteAddressAction`, `editAddressAction`, а также при `updateAddressPriceAction`/`updateDeliveryPriceAction`, если `addressId` приходит с клиента и используется для расчёта (минимум — не позволять использовать чужой адрес для получения цены зоны).

Дополнительно: во всех экшенах добавить проверку авторизации:
```php
if (!$USER->IsAuthorized()) {
    return ['success' => false, 'error' => 'Требуется авторизация'];
}
```

### 12.3 Критерии приёмки
- Запрос `deleteAddress`/`editAddress` с ID чужого адреса → `success: false`, изменения не применяются.
- Неавторизованный запрос любого экшена → `success: false`.

## 23. Регрессионный чек-лист (после каждого этапа)

**Корзина**
- [ ] Изменение количества «+/−», в т.ч. быстрые клики (debounce, блокировка кнопок).
- [ ] Удаление товара, удаление последнего товара (переход в пустое состояние).
- [ ] Очистка корзины, сброс купонов, сброс подарка.

**Подарки**
- [ ] Выбор/смена/отмена подарка, появление и удаление позиции.
- [ ] Снижение суммы ниже порога, лимит «один подарок».
- [ ] Сумма с подарком не растёт; порог не «съедается» подарочной позицией.

**Промокод**
- [ ] Применение валидного/невалидного/просроченного промокода.
- [ ] Отмена промокода, повторное применение.
- [ ] Взаимоисключение с подарком и бонусами.

**Доставка и адреса**
- [ ] Самовывоз (ресторан), доставка (адрес), недоступный адрес/ресторан.
- [ ] Добавление/редактирование/удаление адреса, в т.ч. чужого ID (запрос вручную).
- [ ] Пересчёт суммы и времени доставки, «как можно скорее» и «выбрать дату/время».

**Оформление**
- [ ] Блокировка кнопки при минимальной сумме, разблокировка при достижении.
- [ ] Валидация обязательных свойств, оплаты, даты/времени.
- [ ] Успешное сохранение заказа; в заказе: подарок (позиция + свойство `GIFT`), скидка, доставка, комментарий.

**Интерфейс**
- [ ] Desktop и mobile, а также приложение (`fisheat_app`/`mobile_app`).
- [ ] Уведомления об ошибках видны пользователю.
- [ ] Композит выключен: разметка соответствует сессии в двух браузерах.

**Технические проверки**
- [ ] `php -l` для изменённых PHP, `node --check` для JS.
- [ ] В логах нет notice/warning от компонента.
- [ ] Нет записей `UPDATE b_sale_delivery_srv`/создания свойств при обычных хитах.
